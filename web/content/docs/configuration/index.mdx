All backend settings live in one file: `config.toml`. The shipped
`config.example.toml` documents every option inline and is copied into place
on first boot if no config exists.

## File location

By default the config is read from `/app/config/config.toml`. In the standard
Docker setup that path is bind-mounted from `./config/` on the host
(`./config:/app/config`).

Two environment variables change the location:

- `MIRAMEDIA_CONFIG_FILE` — full path to the TOML file. Takes precedence over everything.
- `MIRAMEDIA_CONFIG_DIR` — directory containing `config.toml` (default `/app/config`).

These two control _where_ the config is read from, so they are read directly
from the environment at startup.

## Secrets and environment variables

Every config value can be overridden by an environment variable. The rule:
uppercase the path, join sections with `__`, and prefix with `MIRAMEDIA_`.

```toml
[auth]
token_secret = "your-secret"

[auth.openid_connect]
client_secret = "from-provider"
```

becomes

```text
MIRAMEDIA_AUTH__TOKEN_SECRET=your-secret
MIRAMEDIA_AUTH__OPENID_CONNECT__CLIENT_SECRET=from-provider
```

Environment variables **override** the TOML file (precedence, highest to
lowest: process env → `.env` → TOML file). Use them for secrets so credentials
stay out of `config.toml`.

<Callout type="warn">

Config-value overrides use the `MIRAMEDIA_` prefix with `__` nesting. Some
operational variables also take the prefix (`MIRAMEDIA_CONFIG_DIR`,
`MIRAMEDIA_CONFIG_FILE`, `MIRAMEDIA_LOG_FILE`), while a few are bare (`PORT`,
`BASE_PATH`). The names are not uniform — see
[Environment Variables](../advanced-features/environment-variables).

</Callout>

## Settings UI vs. file

Most settings can also be edited from **System → Settings** in the dashboard.
Those overrides are stored in the database and layered on top of the file, so
the effective order is: **DB overrides → environment → `.env` → `config.toml`
→ built-in defaults**.

Saving applies immediately — no restart. Every editable section (`misc`,
`auth`, `notifications`, `torrents`, `indexers`, `metadata`, `requests`,
`subtitles`, `updates`, `cloudflare`, `imports`, `streams`, `playback`) is
swapped on the live config,
schedule intervals are rescheduled, and auth transport settings (cookie flags,
session lifetime, OIDC client) are rebuilt in place. Other workers pick the
change up over the event bus. The one exception is `auth.token_secret`, which
is restart-only — a DB override for it is ignored by the live apply so
in-flight sessions aren't invalidated mid-request.

Saves are compare-and-swap against a settings revision: a concurrent edit is
rejected rather than silently overwriting, and a failed apply rolls back to the
previous revision.

<Callout type="info">

`config.toml` remains the file-level source of truth and is what a fresh
install reads; UI overrides sit on top of it. A field showing an
`overridden` badge is coming from the database, not the file — reset it there
if editing the file appears to do nothing.

</Callout>
