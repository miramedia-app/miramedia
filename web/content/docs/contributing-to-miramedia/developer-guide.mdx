## Source Code directory structure﻿

- `miramedia/`: Backend FastAPI application
- `web/`: Frontend Next.js application (React 19, Tailwind v4, shadcn/ui, static export SPA)
- `web/content/docs/`: This documentation (Fumadocs MDX)
- `alembic/`: Database migrations
- `tests/`: Backend test suite (`tests/integration/` holds the Postgres-only suites)

The backend is split per domain — `shows`, `movies`, `torrents`, `indexers`,
`imports`, `streams`, `subtitles`, `metadata`, `auth`, `notifications`,
`requests`, `logs`, `settings`, `updates` — each following a
**router / service / repository** split and mounted under
`/api/v1/{domain}/`. Pluggable providers live in a module's `backends/`
(indexer backends, request backends, …); `indexers/sites/` holds the native
scraper definitions.

Shared pieces worth knowing:

- `main.py` — app assembly and router wiring; `startup.py` — boot sequence.
- `core/router.py` — health, feature flags, dashboard summary, static images.
- `config.py` — pydantic-settings TOML loader; per-domain `config.py` modules
  define each section's schema.
- `settings/` — the DB-backed override layer behind **System → Settings**
  (validation, compare-and-swap mutation, live reload).
- `imports/` — the import pipeline: `files.py`, `matching.py`, the
  `archive_*` modules (safe extraction/publication), and the queue.
- `subtitles/arr_shim/` — the read-only Sonarr/Radarr compatibility surface
  Bazarr talks to, mounted outside `/api/v1` at `/sonarr` and `/radarr`.
- `scheduler.py` — taskiq scheduler; `observability/` and `ops/` — Web Vitals
  ingest and operator endpoints.

<Callout type="warn">

A new SQLAlchemy model must be imported in `alembic/env.py`, or autogenerate
won't see it.

</Callout>

## Special Dev Configuration﻿

### Environment Variables﻿

MiraMedia uses various environment variables for configuration. In the Docker development setup (`docker-compose.dev.yaml`), most of these are automatically configured for you.

#### Backend Variables﻿

- `BASE_PATH`\
  Base path for the app (for subdirectory deployments).
- `PUBLIC_VERSION`\
  Version string reported by `GET /api/v1/system/version` and included in the
  superuser `GET /api/v1/health/details` payload. Injected at image build from
  the release tag; falls back to the packaged version when unset.
- `FRONTEND_FILES_DIR`\
  Directory for built frontend files (e.g. `/app/web/build` in Docker).
- `MIRAMEDIA_MISC__DEVELOPMENT`\
  When set to `TRUE`, enables FastAPI hot-reloading in Docker.

#### Frontend Variables﻿

- `NEXT_PUBLIC_API_URL` (or legacy `PUBLIC_API_URL`)\
  API URL for backend communication.
- `PUBLIC_VERSION`\
  Version string displayed in the frontend UI (mapped to `NEXT_PUBLIC_VERSION` at build time).
- `BASE_PATH`\
  Base path for frontend routing (matches backend `BASE_PATH`); applied via Next.js `basePath`.

#### Docker Development Variables﻿

- `MIRAMEDIA_DISABLE_FRONTEND_MOUNT`\
  When `TRUE`, the backend does not serve the built frontend (set this when a
  reverse proxy or a separate dev server serves the SPA instead).

<Callout type="info">

In `docker-compose.dev.yaml` the `web` service runs the Next dev server on
port 5555 for live editing; the `api` service still serves its own baked build
on 8001. This variable is **not** set there — set it yourself only if you want
the backend to stop serving the SPA entirely.

</Callout>

#### Configuration Files﻿

- Backend: `res/config/config.toml` (created from `config.dev.toml`)
- Frontend: `web/.env` (created from `.env.example`)

### Recommended Development Workflow﻿

The recommended way to **run** MiraMedia during development is the Dockerized setup with `docker-compose.dev.yaml`. It matches production closely and provisions PostgreSQL, hot-reload, and the dev servers without a local backend or frontend runtime.

Quality gates (`make check`, `make check-ci`) are **not** containerized: they run on the host with `uv`, Python 3.13, and `pnpm`. You can develop entirely in Docker and still run the gates on the host once those tools are installed.

The development environment includes:

- Backend (FastAPI) with automatic hot-reloading for Python code changes
- Frontend (Next.js 16) with Turbopack Fast Refresh for instant updates
- Database (PostgreSQL) pre-configured and ready to use

#### What supports hot reloading and what does not﻿

- Python code changes (.py files), Frontend code changes (.tsx, .ts, .css) and configuration changes (config.toml) reload automatically.
- Changing the backend dependencies (pyproject.toml) requires rebuilding: `docker compose -f docker-compose.dev.yaml build api`
- Changing the frontend dependencies (package.json) requires restarting the web container: `docker compose -f docker-compose.dev.yaml restart web`
- Database migrations: Automatically run on backend container startup

This approach eliminates the need for container restarts during normal development and provides the best developer experience with instant feedback for code changes.

#### How the Frontend Connects to the Backend﻿

The Next.js frontend talks directly to the backend over CORS:

- Frontend (Next dev server) runs on: `http://localhost:5555` (mapped from container port 5173)
- Backend runs on: `http://localhost:8001` (mapped from container port 8000)
- `NEXT_PUBLIC_API_URL` is left **empty** in `docker-compose.dev.yaml`, so the SPA uses relative `/api/*` URLs that the Next dev rewrite (`next.config.ts`) proxies to `api:8000` internally. Relative URLs are required so a browser on a LAN IP (not just `localhost`) reaches the right backend. Cookie-based auth uses `credentials: 'include'`; the backend whitelists the frontend origin via `MIRAMEDIA_MISC__CORS_URLS`.

### Setting up the full development environment with Docker (Recommended)﻿

### Prepare config files

Create config directory (only needed on first run) and copy example config files:

```bash
mkdir -p res/config # Only needed on first run
cp config.dev.toml res/config/config.toml
cp web/.env.example web/.env
```

### Start all services

Recommended: Use make commands for easy development

```bash
# Recommended: Use make commands for easy development
make up
```

Alternative: Use docker compose directly (if make is not available)

```bash
docker compose -f docker-compose.dev.yaml up
```

### Access the application

- Frontend (with HMR): http://localhost:5555
- Backend API: http://localhost:8001
- Database: localhost:5433

The bootstrap admin credentials are printed in the logs accessible with `make logs`.

Now you can edit code and see changes instantly:

- Edit Python files → Backend auto-reloads
- Edit React/TypeScript files → Next.js Fast Refresh updates in browser
- Edit config.toml → Changes apply immediately

<Callout type="info">

Run `make help` to see all available development commands including `make down`, `make logs`, `make app` (shell into backend), and more.

</Callout>

## Setting up the backend development environment (Local)

### Clone & prerequisites

1. Clone the repository
2. cd into repo root
3. Install `uv`: https://docs.astral.sh/uv/getting-started/installation/
4. Verify installation:

```bash
uv --version
```

### Install Python with uv

```bash
uv python install 3.13
```

### Create virtual environment

```bash
uv venv --python 3.13
```

### Install dependencies

```bash
uv sync
```

### Run database migrations

```bash
uv run alembic upgrade head
```

### Run the backend (development mode)

```bash
uv run --python 3.13 fastapi run miramedia/main.py --reload --port 8001
```

<Callout type="warn">

Always pass `--python 3.13` to `uv run`. The `libtorrent` wheel used by the
native download client is published for cp313 only, so a newer interpreter
breaks the install. CI pins `UV_PYTHON=3.13` for the same reason.

</Callout>

### Host prerequisites for quality gates

Before running `make check` or `make check-ci` on the host:

1. Install [uv](https://docs.astral.sh/uv/getting-started/installation/) and sync the backend:
   `uv python install 3.13 && uv sync`
2. Install [pnpm](https://pnpm.io/installation) (the repo pins it via `web/package.json`).
3. Bootstrap the frontend once per fresh clone:
   `make frontend-bootstrap` (installs `web/` deps and generates Fumadocs collections + Next type declarations).

`make up` starts the application stack in Docker; it does **not** install these host toolchains or run the quality gates for you.

### The quality gate

`make check` is the **fast local gate** — run it often while developing on the host (after the prerequisites above). It chains:

| Step                    | Command                | Covers                                     |
| ----------------------- | ---------------------- | ------------------------------------------ |
| `lint`                  | `ruff check .`         | Backend lint                               |
| `format-check`          | `ruff format --check`  | Backend formatting                         |
| `ty`                    | `ty`                   | Backend type check (config in `pyproject.toml` under `[tool.ty]`) |
| `test`                  | `pytest`               | Backend suite — **no live Postgres needed**; keep it that way |
| `tsc`                   | `pnpm typecheck`       | Frontend types                             |
| `frontend-test`         | `vitest`               | Frontend unit tests (Node-only, no backend) |
| `frontend-lint`         | oxlint + oxfmt format check | Frontend lint                          |
| `migration-head-audit`  | Alembic head audit     | Divergent migration heads                  |

`make check-ci` is the **slower pre-PR CI-parity gate**. Run it on the host before opening a PR when you have the prerequisites above **plus** a disposable PostgreSQL database (`MIRAMEDIA_TEST_DATABASE_URL`) and Playwright Chromium installed. It runs `make check`, then the CI jobs that `check` deliberately skips:

| Step             | Command / target       | Covers                                              |
| ---------------- | ---------------------- | --------------------------------------------------- |
| `frontend-build` | `pnpm build`           | Production static export                            |
| OpenAPI drift    | `make openapi` + diff  | Regenerates `web/public/openapi.json` and `web/src/lib/api/api.d.ts`; fails if either file drifts from the committed copy |
| `integration-test` | `pytest -m integration` / `postgresql` | PostgreSQL-backed suites (requires `MIRAMEDIA_TEST_DATABASE_URL`) |
| `frontend-e2e`   | `pnpm run test:e2e`    | Playwright browser smoke suite (install Chromium once: `cd web && pnpm exec playwright install --with-deps chromium`) |
| `frontend-smoke-real` | `pnpm run test:smoke` | Real frontend→FastAPI→PostgreSQL smoke on port **43219** (`GET /api/v1/health` must report `db.ok`); needs `make frontend-build`, Chromium, and `MIRAMEDIA_TEST_DATABASE_URL` |

Related targets:

- `make format` — apply backend formatting.
- `make openapi` — regenerate `web/public/openapi.json` and
  `web/src/lib/api/api.d.ts` from the backend schema. Run it after **any**
  change to request/response shapes (and commit both files when they change).
- `make integration-test` — the PostgreSQL-backed suites, which `make test`
  deliberately does not collect. Needs `MIRAMEDIA_TEST_DATABASE_URL` pointing at
  a disposable database.
- `make frontend-e2e` — the Playwright browser smoke suite. Install Chromium
  once with `cd web && pnpm exec playwright install --with-deps chromium`.
- `make frontend-smoke-real` — one real browser workflow against FastAPI serving
  the static export plus disposable PostgreSQL (`scripts/smoke_stack.py` on port
  **43219**, health at `/api/v1/health`). Requires `make frontend-build`,
  Chromium, and `MIRAMEDIA_TEST_DATABASE_URL`.
- `make migration-head-audit` — checks for divergent Alembic heads.
- `make audit` — `pip-audit` over locked prod deps plus `pnpm audit`.

## Setting up the frontend development environment (Local, Optional)

### Clone & change dir

1. Clone the repository
2. cd into repo root
3. cd into `web` directory

### Install Node.js (example using nvm-windows)

I used nvm-windows:

```powershell
nvm install 24.1.0
nvm use 24.1.0
```

If using PowerShell you may need:

```powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

### Create .env for frontend

```bash
cp .env.example .env
```

Update `NEXT_PUBLIC_API_URL` if your backend is not at `http://localhost:8001`

### Install dependencies and run dev server

```bash
pnpm install
pnpm dev
```

<Callout type="warn">

On a fresh clone `pnpm install --frozen-lockfile` is **not** enough: pnpm 10
blocks postinstall scripts, so the Fumadocs collections (`web/.source`) and
Next's type declarations are missing. Use `make frontend-bootstrap` (install +
generate), or run `pnpm run generate` before typechecking. `pnpm build` and
`pnpm run generate` each invoke `fumadocs-mdx` themselves — never wrap another
generation step around them.

</Callout>

### Format & lint

- Format:

```bash
pnpm format
```

- Lint:

```bash
pnpm lint
```

<Callout type="info">

If running the frontend locally, add the dev server's origin (e.g.
`http://localhost:3000`) to `cors_urls` in your backend config file.

</Callout>

## Troubleshooting﻿

### Common Docker Development Issues﻿

<details>

<summary>Port already in use errors</summary>

- Check if host ports 5555, 8001, or 5433 are already in use:
  - macOS/Linux: `lsof -i :5555`
  - Windows: `netstat -ano | findstr :5555`
- Stop conflicting services or change ports in `docker-compose.dev.yaml`

</details>

<details>

<summary>Container not showing code changes</summary>

- Verify volume mounts are correct in `docker-compose.dev.yaml`
- For backend: Ensure `./miramedia:/app/miramedia` is mounted
- For frontend: Ensure `./web:/app` is mounted
- On Windows: Check that file watching is enabled in Docker Desktop settings

</details>

<details>

<summary>Frontend changes not updating</summary>

- Check that the frontend container is running: `make ps` or `docker compose -f docker-compose.dev.yaml ps`
- Verify Next.js Fast Refresh is working (should see HMR updates in the browser console)
- Try restarting the frontend container:

```bash
docker compose -f docker-compose.dev.yaml restart web
```

</details>

<details>

<summary>Backend changes not reloading</summary>

- Verify `MIRAMEDIA_MISC__DEVELOPMENT=TRUE` is set in `docker-compose.dev.yaml`
- Check backend logs:

```bash
make logs ARGS="--follow api"
# or
docker compose -f docker-compose.dev.yaml logs -f api
```

- If dependencies changed, rebuild:

```bash
docker compose -f docker-compose.dev.yaml build api
```

</details>

<details>

<summary>Database migration issues</summary>

- Migrations run automatically on container startup
- To run manually:

```bash
make app
uv run alembic upgrade head
```

- To create new migration:

```bash
make app
uv run alembic revision --autogenerate -m "description"
```

- Downgrade floor: the squashed initial schema revision is the lowest supported
  Alembic revision. `alembic downgrade base` (or `-1` from that revision) is
  refused because reversing it would drop unrelated objects in `public`. Use a
  disposable database or restore from backup instead.

- Specials skip backfill (`c8d2e3f4a5b6`): that revision read live
  `misc.download_specials` once and may have marked Season 0 rows skipped when
  the setting was off. The destructive branch is irreversible and cannot be
  distinguished from later user skip edits — do not mass-rewrite `skipped`
  flags to “fix” historical databases. Revision `g5c6d7e8f9a0` adds the
  read-only `specials_skip_audit` view for operator review instead:

  ```sql
  SELECT * FROM specials_skip_audit ORDER BY show_name, episode_number;
  ```

  `skip_category` is a reporting hint (`wanted_undownloaded`, `skipped_undownloaded`,
  `downloaded`), not grounds for automatic correction.

</details>

<details>

<summary>Viewing logs</summary>

- All services: `make logs`
- Follow logs in real-time: `make logs ARGS="--follow"`
- Specific service: `make logs ARGS="api --follow"`

</details>

<details>

<summary>Interactive debugging (shell into containers)</summary>

- Shell into backend:

```bash
make app
# or
docker compose -f docker-compose.dev.yaml exec -it api bash
```

- Shell into frontend:

```bash
make frontend
# or
docker compose -f docker-compose.dev.yaml exec -it web sh
```

- Once inside, you can run commands like `uv run alembic upgrade head`, `pnpm install`, etc.

</details>

<details>

<summary>Volume permission issues (Linux)</summary>

- Docker containers may create files as root, causing permission issues, which can make the login page fail to show up.

Solution:

```bash
sudo chown -R $USER:$USER res/
```

- Alternatively: Run containers with your user ID or use Docker's `user:` directive (may fail in some setups).

</details>

<details>

<summary>Complete reset</summary>

If all else fails, you can completely reset your development environment:

```bash
make down
docker compose -f docker-compose.dev.yaml down -v  # Remove volumes
docker compose -f docker-compose.dev.yaml build --no-cache  # Rebuild without cache
make up
```

</details>
