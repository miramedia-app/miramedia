## Prerequisites

- Docker and Docker Compose installed.
- If you plan to use OAuth 2.0 / OpenID Connect, an account and client
  credentials from an OIDC provider (Authentik, Pocket ID, Keycloak, etc.).

<Callout type="info">

The default `:latest` image is slim and ships a libtorrent client but **no**
Chromium. The in-process Cloudflare `native` solver needs Chromium + Xvfb, which
are bundled only in the **`-cf`** variant — a separate repository,
`ghcr.io/miramedia-app/miramedia-cf:<version>` — so pull that if
you enable `[cloudflare]` with `solver = "native"` (budget ~2 GB RAM for the
`api` container; the compose file sets this limit). On low-RAM NAS hardware,
follow the [Synology guide](synology) for tuned concurrency, or keep the bypass
off with `enabled = false` under `[cloudflare]` in `config.toml`. External
solvers (`byparr`/`flaresolverr`/`remote`/`browser_run`/`firecrawl`) need no
local Chromium and run on the slim image.

</Callout>

## Architecture

The default `docker-compose.yaml` defines two services:

| Service | Container            | Image                                    | Purpose                                   |
| ------- | -------------------- | ---------------------------------------- | ----------------------------------------- |
| `api`   | `miramedia`          | `ghcr.io/miramedia-app/miramedia:latest` | API + web UI + scheduler (single process) |
| `db`    | `miramedia-postgres` | `postgres:17-alpine`                     | PostgreSQL database                       |

The `api` service serves both the REST API and the static frontend on
host port `8000` — front it with your own reverse proxy (nginx, Caddy,
DSM, Traefik, …) if you want HTTPS on a custom hostname. Port `6881`
(TCP and UDP) is published for the built-in native torrent client.
Database migrations and the background scheduler run inside the `api`
container automatically — there is no separate worker by default. For
multi-worker deployments you can move the scheduler into a dedicated sidecar
(see the commented `miramedia-scheduler` block in `docker-compose.yaml` and
the `MIRAMEDIA_WEB_WORKERS` / `MIRAMEDIA_SCHEDULER_DISABLED` notes); single-host
NAS installs should stay on the in-process default.

## Setup

#### Get the compose file

```bash
wget -O docker-compose.yaml https://github.com/miramedia-app/miramedia/releases/latest/download/docker-compose.yaml
```

#### Prepare the config directory

```bash
mkdir config
wget -O ./config/config.toml https://github.com/miramedia-app/miramedia/releases/latest/download/config.example.toml
```

If you skip this step, the container copies `config.example.toml` to
`/app/config/config.toml` on first boot. Either way the entrypoint replaces the
`CHANGE_ME_GENERATE_RANDOM_STRING` placeholder with a generated
`auth.token_secret` (on first boot, and again later if the placeholder is still
there), so the app starts with a persistent secret and sessions survive
restarts.

#### Edit the configuration

At minimum set `misc.frontend_url`, `misc.cors_urls`, and a stable
`auth.token_secret`. See [Configuration](../configuration) for everything
else.

#### Start the stack

```bash
docker compose up -d
```

On first run MiraMedia:

- runs Alembic migrations,
- creates a bootstrap admin user **because the user table is empty** — the
  generated credentials are printed in the container logs. Log in and change
  the password immediately.

<Callout type="info">

Superusers are managed from the dashboard at **System → Users** — there is no
longer a required `admin_emails` setting. The legacy `auth.admin_emails`
option still promotes matching accounts on startup but is deprecated; prefer
the UI.

</Callout>

## Volumes and paths

The compose file bind-mounts:

- `./config/` → `/app/config/` — holds `config.toml`.
- `./data/` → `/data/` — media + downloads (`show_directory`,
  `movie_directory`, `torrent_directory` under `[misc]`). Pre-create
  `./data/{shows,movies,torrents}` on the host so imports can hard-link across
  them under one mount.
- `./images/` → `/app/images/` — poster / metadata image cache, kept out of
  the media tree.
- `/var/run/docker.sock` → `/var/run/docker.sock` — read-write, **required for
  in-app updates** (`updates.allow_in_app_apply`). Comment it out to disable
  one-click updates.

Hard-linking only works within a single filesystem. Keep your downloads and
your media library on the **same volume/mount** or imports fall back to slow
copies (and may fail on space). See
[Troubleshooting](../troubleshooting#hard-linking).

## Container runtime

- The container **starts as root**, fixes ownership on `/app/config` and
  `/data`, then drops to the unprivileged `miramedia` user via `gosu` for
  migrations and the server itself. Nothing long-running stays root.
- While still root it also matches the mounted Docker socket's GID and adds
  the app user to that group, so in-app updates work without extra compose
  wiring. This only applies when the service runs as root — pin a non-root
  `user:` and you must supply
  [`group_add`](../configuration/updates#in-app-apply-opt-in) yourself.
- Both services set `security_opt: [no-new-privileges:true]`, which blocks
  setuid escalation inside the container. Keep it. The Synology compose adds
  `seccomp:unconfined` on top for the Chromium `clone3()` issue — see the
  [Synology guide](synology).

## Docker images

Images are published to GitHub Container Registry:

- `ghcr.io/miramedia-app/miramedia` — slim (default).
- `ghcr.io/miramedia-app/miramedia-cf` — same app plus Chromium + Xvfb, for
  the Cloudflare `native` solver.

### Tags

- `latest` — latest stable release. **Slim repo only** — the `-cf` repo
  publishes version tags but no `latest`.
- `X.Y.Z`, `X.Y`, `X` — version pins (e.g. `1.0.13`, `1.0`, `1`), published to
  both repos.

Images are built only on tagged releases, so there is no rolling
branch/PR tag — pin a version if you don't want `latest` to move under you.

<Callout type="info">

A `401`/`403` from GHCR is almost always a misconfigured Docker client, not
an image-permissions issue. Run `docker logout ghcr.io && docker pull
ghcr.io/miramedia-app/miramedia:latest`, or see
[GitHub Container Registry troubleshooting](https://stackoverflow.com/questions/74656167/unable-to-pull-image-from-github-container-registry-ghcr).

</Callout>
